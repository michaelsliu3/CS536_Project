\begin{abstract}
We study whether selecting context for each code change can reduce the input cost of LLM-assisted code review without reducing accuracy. Our planned method trains a small context selector while keeping the reviewer fixed. So far, we have prepared a repository-based split of 46,518 ContextCRBench examples, completed a Qwen3B QLoRA training pilot, and implemented fixed, random, and similarity-based context policies. This report describes the audited data and training setup. Evaluation outputs are under review, so we do not yet draw conclusions about adaptation or context selection.
\end{abstract}
\noindent\textbf{Repository:} \url{https://github.com/michaelsliu3/CS536_Project}

\section{Research question}
A code reviewer may need an issue description to understand a change's purpose or nearby code to see how it will be used. Giving the model every available field uses more tokens, even when some fields add little useful information. We ask: \emph{Can a learned selector choose context for each code change while maintaining review accuracy and using fewer tokens than fixed context choices?}

ContextCRBench provides code changes together with issue, pull request (PR), and surrounding-code context \citep{hu2025}. Repoformer studies selective retrieval for code completion \citep{wu2024}; we ask whether a separate selector can help with code-review judgments. Following instructor feedback, we focus on the accuracy--cost trade-off.

Our target is accuracy within one percentage point of the best fixed strategy with at least 30\% fewer extra context tokens, or higher accuracy at a matched budget. The Qwen3B adaptation pilot checks the data and evaluation pipeline and asks whether fine-tuning improves merge-status prediction. It is separate from the main experiment, which will keep Qwen frozen and train the selector.

\section{Data and experimental setup}
\paragraph{Task and split.}
The reviewer returns a JSON answer with the Boolean field \texttt{is\_merged}. Merge status is our benchmark target, but only a proxy for code quality: a merged change can contain a bug, and a rejection can have nontechnical reasons. We exclude explicit outcome fields and human review answers from prompts. Later edits and quoted solutions in issue and PR text still need a chronology audit.

The downloaded release contains 68,938 JSON records. Cleaning removes 22,375 exact normalized-diff duplicates and excludes 45 records from 16 groups with conflicting labels, leaving 46,518 examples from 99 repositories. With seed 42, we target an 80/10/10 split by repository; all changes from one PR remain together. The saved manifest has disjoint repository sets (Table~\ref{tab:data}). Unequal repository sizes explain the different example proportions. We use validation for development and reserve test repositories for the final comparison. This split does not rule out near-duplicates or temporal leakage.

\paragraph{Model and adaptation method.}
The audited pilot uses Qwen2.5-Coder-3B-Instruct, a decoder-only Transformer with 36 layers, hidden size 2,048, and feed-forward size 11,008. Grouped-query attention uses 16 query heads and two key/value heads. The model generates the JSON verdict autoregressively. Although its configuration supports 32,768 positions, our experiment limits each sequence to 2,048 tokens.

QLoRA \citep{dettmers2023} freezes the base weights in 4-bit NF4 with double quantization and bfloat16 computation. We train low-rank adapters on the attention query, key, value, and output projections and the feed-forward gate, up, and down projections. Rank 16, scaling $\alpha=32$, and dropout 0.05 give 29,933,568 trainable parameters. The saved run uses paged 8-bit AdamW, learning rate $2\times10^{-4}$, cosine decay, 3\% warmup, and weight decay 0.01. Batch size one with eight accumulation steps gives an effective batch size of eight. Training ran for three epochs (14,289 optimizer steps) on one 32-GB RTX 5090; the final adapter is \texttt{checkpoint-14289}.

Inputs contain repository and language metadata, the diff, issue and PR text, and code before and after the change. Training supervises only the JSON answer and end-of-sequence token; prompt tokens are masked from the loss. Right truncation keeps the sequence within 2,048 tokens. After preprocessing, 63.3\% of training and 57.2\% of validation sequences reach this cap. These are post-truncation lengths, not measurements of how many tokens were discarded.

\paragraph{Evaluation and context policies.}
Evaluation compares the untouched base, the trained adapter, and a constant prediction chosen from training-label counts on the same saved 200 examples. The two model conditions share prompts, quantization, and deterministic decoding, with at most 2,016 input tokens and 32 generated tokens. Invalid JSON counts as an error and is reported separately. We will compare accuracy, macro-F1, per-class scores, and paired improvements and regressions.

For the frozen-reviewer study, diff-only, all-context, fixed-mask, random, and BM25 similarity policies are implemented. They select among issue text, PR text, and code before and after the change; the diff is always present. Assembled prompts are checked against token budgets. We plan to train a compact Transformer selector from reviewer outcomes on training repositories. The selector has not been trained, and context-policy comparisons remain pending. Fixed masks and budgets will be chosen on validation data.

\section{What we learned}
Cloud runs made recovery a practical requirement. Checkpoints now retain adapter, optimizer, scheduler, and random states. We changed validation from every 100 to every 1,000 optimizer steps and corrected the restored interval on resume; timing measurements are still needed to assess the effect. The data audit also shows why accuracy alone is insufficient: labels are imbalanced, language mix changes across repositories, and many inputs reach the token cap. An all-context prompt does not guarantee that the reviewer sees every field. We need to check context timing and truncation before interpreting differences between models.

\section{Next steps}
Our immediate task is to resolve the evaluation checks, fill Table~\ref{tab:pilot}, and inspect improvements and regressions on held-out repositories. Pilot findings will be reported separately from the context-selection experiment.

We will then run a small frozen-reviewer comparison to check whether context choices change enough judgments to make per-example selection useful. If they do, we will generate training outcomes and train the selector. Comparisons will include accuracy, extra context tokens, and runtime including selection, followed by repeated seeds and context-type ablations. If the selector does not beat the best fixed policy, we will analyze where context helps or hurts and report that result.
